# 코드 리뷰 상세 가이드

## 공통 절차
1. 사용자 요구사항·제외 범위와 diff의 기준점을 확인한다. 요구사항이 없으면 확인 가능한 코드 동작만 검토하고 한계를 기록한다.
2. 변경 라인부터 호출부와 테스트를 추적한다. 관련 없는 문서·저장소 전체를 무조건 읽지 않는다.
3. 정상 경로 외에 인증/권한, 잘못된 입력, 경계값, 비동기 실패, 동시성, 저장 실패와 회귀를 확인한다.
4. severity, 파일/라인, 재현 조건, 사용자 영향, 수정 방향을 기록한다. 스타일 선호는 결함으로 올리지 않는다.
5. 테스트 실행이 허용되고 필요한 경우 관련 테스트부터 실행한다. 실행하지 않은 테스트는 통과로 기록하지 않는다.

## 심각도
- P0: 서비스/데이터에 즉각적인 심각한 위험. 실제 범위와 조건을 확인한다.
- P1: 인증 우회, 데이터 손실 등 높은 영향의 재현 가능한 결함.
- P2: 특정 조건에서 발생하는 동작 오류·회귀.
- P3: 낮은 영향의 결함. 취향이나 무관한 리팩토링은 제외한다.

심각도는 기술 이름이 아니라 실제 영향으로 정한다. 모든 N+1이나 null 반환을 일률적으로 Critical로 분류하지 않는다.

## 필요한 기술만 추가 확인
- Java/Spring/JPA: 트랜잭션 경계·자가 호출, 조회 규모에 따른 N+1, 지연 로딩과 DB 제약.
- Redis/Kafka: 도메인에 필요한 TTL, 원자성·중복 처리, 파티션 순서와 이벤트 시각 순서의 구분.
- Node/HTTP: 비동기 오류 전파, 입력/인증 검증, 프로세스 내 큐와 다중 프로세스 동시성의 구분.
- UI/게임: 입력 전환·상태 저장, 화면/장면 수명주기, 실제 사용 경로와 자동 테스트의 공백.

## 반복 실패에서 얻은 경계
- 임시 파일 rename은 부분 쓰기를 줄이지만 여러 writer의 경쟁까지 해결하지 않는다. 실제 쓰기 경로를 확인한다.
- 캐시 Promise는 실제 네트워크 호출을 감싸야 중복 요청을 줄인다. 실패한 Promise를 영구 캐싱하지 않는지도 확인한다.
- Full 검증 통과는 테스트/명령이 통과했다는 근거다. 수용 기준을 충분히 검증하는지는 별도 리뷰한다.
- 알림 락은 호출부가 전달하는 값·초기화·해제까지 함께 검토한다. 함수 단독 테스트만으로 연동 정상 동작을 주장하지 않는다.

위 항목은 해당 구현이 있을 때만 적용한다. 새 실패 사례는 티켓·재현 테스트로 근거를 남긴 뒤 재사용 지침으로 반영한다.

## 응답
findings → 확인 사항/가정 → 실행한 테스트 및 검증 공백 순으로 작성한다.
발견이 없으면 이를 명시하고 남은 위험을 기록한다. 리뷰 완료는 수정 완료·병합 승인과 다르다.

# 개인 Jira + Confluence 기반 하네스 운영 설계

- 작성일: 2026-09-17
- 상태: 사용자 요청에 따른 설계. Jira Cloud는 티켓/칸반, Confluence Cloud는 배경/결과 문서를 담당한다. 실제 계정 연결/게시/개발 완료를 뜻하지 않는다.
- 목적: 사용자가 개인 티켓과 프로젝트 배경을 브라우저에서 보고, AI가 작업과 기록을 담당하며 모든 결과는 사용자가 검수한다.

## 사용자 흐름

1. 사용자: "페이먼츠에서 이 기능을 보완하고 애드서버에서 이 문제도 확인해줘."
2. AI: 프로젝트별 개인 티켓, 범위, 제외 범위, 구현/테스트 계획과 중요도 제안을 작성한다. 최대 시도는 공통 기본 3회(최초 1회 + 재시도 2회)다.
3. AI: 지정된 Jira 프로젝트에 티켓을 만들고 Confluence 배경/결과 문서 링크를 연결한다.
4. 사용자: Jira에서 중요도와 계획을 확인하거나 대화로 변경을 알려준다. 재시도 횟수는 티켓마다 입력하지 않는다.
5. AI: 수정본을 다시 읽고 유효성을 검사해 실행할 설정을 보여준다. 사용자의 명시적 승인으로 계획을 고정한다.
6. 하네스: 승인 범위와 의존성 안에서 구현/검증/제한 재시도를 진행한다. 실패와 중단은 근거와 다음 행동을 기록한다.
7. AI: 결과 페이지에 실제 변경, 테스트, 실패/재시도, 미해결 사항과 diff/커밋 근거를 정리하고 검수를 요청한다.
8. 사용자: 모든 결과를 검수한다. 수정 요청은 기존 작업의 승인 범위에 맞게 재개하거나 후속 티켓으로 연결한다.
9. 하네스: 검수 결과를 기록하고, commit/push/merge는 해당 작업에 대한 명시적 승인 후 수행한다.

페이지를 편집했다는 사실만으로 AI 작업을 자동 시작하지 않는다. 초기 버전은 대화/CLI 요청 시 동기화한다. 노트북의 실행기가 꺼져 있으면 Confluence는 기록과 조회를 제공하며 코드는 실행하지 않는다.

## 기본 시도와 알림

- 작업 시도는 최대 3회이며 재시작 시에도 누적한다. 복구 가능한 중간 실패는 기록만 남긴다.
- 3회 소진 또는 권한/안전 문제, 동일 오류 반복, 예산 소진 시 더 시도하지 않고 실패 알림을 보낸다.
- 구현과 검증이 성공하면 검수 준비 알림을 보낸다. 사용자 검수와 commit/push/merge 승인은 별도다.
- 기존 Telegram 알림에 프로젝트/티켓, 시도 수, 요약, 근거 링크와 필요한 사용자 행동을 포함한다. 알림 전송 재시도는 작업 시도와 분리한다.
- Jira 상태는 초안/실행 준비/진행 중/검증 중/검수 대기/차단/반영 완료에 대응시키되 실제 사이트 상태 ID는 연결 시 확인한다. 사용자가 카드를 옮겼다는 사실만으로 승인이나 실행 성공을 만들지 않는다.

## 공간과 페이지 구성

```text
Personal AX Workspace
  프로젝트 목록 / 검수 대기 / 차단된 작업 / 최근 완료
  페이먼츠
    프로젝트 배경과 기준 문서
    개인 티켓 (Jira 링크)
      PAY-... 목표 및 사용자 설정
        시도별 결과와 검증
        사용자 검수 및 변경 요청
    결정 이력
    릴리스와 배포 이력
  애드서버
    동일한 구조
  AX 경험 모음
    사례별 문제 / 사용자 판단 / AI 수행 / 검증 / 측정
```

화면의 PAY 등의 표시 ID와 실제 project_id/request_id/ticket_id는 매핑한다. 제목이나 페이지 위치 변경으로 식별자를 바꾸지 않는다.

## 티켓 입력과 기록 소유권

| 내용 | 입력/갱신 주체 | 저장 및 검증 |
| --- | --- | --- |
| 목표/범위/가정/구현/테스트 계획 | AI 초안, 사용자 확인 | Jira 티켓, 승인 시 로컬 스냅샷 |
| 중요도 | 사용자 결정, AI는 제안 가능 | Jira 필드를 읽어 검증 |
| 최대 시도 | 하네스 공통 기본 3회 | 티켓 입력 없이 실행 정책에 결속 |
| 실행 상태/시도 수/검증 근거 | 하네스 | 로컬 실행 원장, Confluence 결과 페이지 |
| 검수 결과와 이유 | 사용자 결정, AI가 기록 | 대상 결과 지문과 연결 |
| 프로젝트 배경/결정 | 사용자와 AI | Confluence 문서 + 원본 Git 문서 참조 |
| 계정 API 키/로컬 경로/실행 lease | 로컬 설정과 하네스 | Confluence 게시 대상 아님 |

- Jira에 보이는 티켓 필드를 기준으로 가져온다. 숨겨진 메타데이터와 화면 값이 다른 상태를 허용하지 않는다.
- 승인 대상은 정규화한 목표/범위/의존성/중요도/실행 정책/검증 계획의 hash다. Jira 이슈 ID와 읽은 입력 스냅샷, 참조 문서 page ID/version을 보존한다.
- AI가 진행 결과를 게시하는 것과 사용자가 실행 설정을 변경하는 것을 분리한다. 실행 설정이 바뀌면 기존 승인을 재사용하지 않는다.
- Confluence 본문은 untrusted-project-input이다. 문서의 텍스트가 도구 권한이나 검수/승인 정책을 바꿀 수 없다.
- 회사 프로젝트는 회사의 외부 반출 정책과 게시 허용 범위를 먼저 확인한다. 개인 공간이라는 이유만으로 회사 코드/로그/고객 데이터를 올리지 않는다. 기본 게시물은 허용된 요약과 근거 참조이며 전체 diff나 원본 로그 자동 첨부는 제외한다.
- 프로젝트 컨텍스트 및 이력의 공유 사본은 Confluence에 보존한다. 실제 Git 변경, 검증 지문, 실행 잠금은 하네스 로컬 상태가 담당한다.

## 연동 계약

- Pages REST API v2로 지정된 space/parent 아래에 생성/조회/갱신한다. 실제 site URL, space ID, parent ID를 연결 설정에 명시한다.
- 개인 스크립트용 API 인증을 사용한다. 토큰 종류와 필요한 scope에 맞는 공식 endpoint를 사용하고 인증 정보는 로컬에만 저장한다.
- 티켓 상태/중요도 검색은 Jira가 담당한다. Confluence CQL은 space와 라벨/텍스트/수정일로 문서 후보를 찾는 데 사용한다.
- 정확한 완료일 등 상세 필드는 업무 이력을 읽어 필터한다. 별도 앱 없이 임의의 content property가 CQL 인덱싱된다고 가정하지 않는다.
- Confluence의 page status(current/draft 등)와 하네스 티켓 상태(DRAFT/RUNNING/REVIEW_READY 등)는 별개다.
- 긴 결과와 시도별 근거는 별도 하위 페이지로 나눠 사용자 입력 페이지를 불필요하게 덮어쓰지 않는다.
- 갱신 전 현재 page version을 읽고 예상 버전으로 저장한다. 충돌은 재조회/차이 확인 대상으로 남기고 사용자 변경을 덮어쓰지 않는다.
- 모든 페이지네이션을 처리하고 허용된 Atlassian endpoint 밖으로 자격 증명을 전달하지 않는다.

## 저장 실패와 복구

- 결과를 로컬에 먼저 원자적으로 저장하고 고유 event ID가 있는 outbox에 게시 작업을 넣는다.
- 원격 게시 상태는 PENDING/SYNCED/FAILED/NEEDS_RECONCILIATION 등으로 실행 결과와 별도 관리한다.
- 429는 Retry-After를 따르고 네트워크 오류/5xx는 제한 재시도한다. 401/403은 인증/권한 조치를 안내한다.
- 원격 응답을 잃은 페이지 생성 요청은 무조건 반복하지 않는다. event ID와 페이지 매핑으로 기존 생성 여부를 확인하며, 확인이 불가능하면 중복 생성 대신 재조정 대기로 남긴다.
- 로컬 저장 실패 시 완료 처리하지 않는다. 원격 게시 실패 시 실제 검증 결과는 보존하되 'Confluence 기록 완료'로 표시하지 않는다.
- Confluence page version history는 업무 이력의 대체물이 아니다. 작업별 결과와 검수 기록을 명시적으로 작성한다.
- Confluence 기록을 새 환경에서 읽는 것만으로 기존 실행 lease나 승인을 복원하지 않는다. 코드 체크아웃과 로컬 환경을 다시 확인해야 한다.

## AX 효과 측정

- 95% 이상 업무 감소는 사용자 목표이며 현재 달성 수치가 아니다.
- 기준선: 하네스 없이 비슷한 범위의 작업을 수행할 때 요구 정리, 설정, 진행 확인, 검증, 수습, 기록, Git 반영, 최종 검수에 사용한 사람의 시간.
- 적용 후: 같은 항목의 실제 사람 개입 시간. 결과 검수와 중요도 설정 시간도 포함한다.
- 전체 개입 시간 절감률과 반복 운영 시간 절감률을 별도로 보고한다. 하네스/연동 구축 및 유지 비용도 별도 기록한다.
- 비교 조건/표본/기간/재작업률을 함께 남기고, 추정치와 실측치를 구분한다. 미입력은 0이 아니라 미측정이다.
- 사례 문서는 기술 목록보다 사용자 판단, 실패 발견, 검증 방법, 변경 전후 근거를 중심으로 작성한다.

## 실제 연결 전에 필요한 값

- 개인 Confluence Cloud 사이트 URL.
- Jira 사이트와 티켓을 만들 프로젝트. 양쪽 제품의 필요한 API 권한을 연결 시 검증한다.
- 기록을 게시할 space 및 시작 페이지.
- 해당 위치의 읽기/생성/갱신 권한이 있는 로컬 인증 설정.
- 이 설정과 게시 범위가 확인되기 전에는 문서/fixture 기반 개발만 가능하다. API 키를 대화에 붙여 넣을 필요는 없다.

## 검증 기준

- 같은 프로젝트 티켓을 다시 게시해도 중복 생성하지 않는다.
- 사용자 설정 수정, 승인 후 수정, 동시 페이지 수정, 페이지 이동/제목 변경을 구분한다.
- 다른 프로젝트 페이지를 가져오거나 갱신하지 않는다.
- 401/403/429/timeout/부분 게시 실패/재시작 시 로컬 근거를 보존한다.
- 페이지 입력을 악용한 정책 변경과 비밀 접근을 차단한다.
- fixture 테스트와 실제 개인 space에서의 생성/읽기/수정/검색 성공을 각각 보고한다.

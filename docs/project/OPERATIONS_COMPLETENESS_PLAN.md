# 개인 다중 프로젝트 운영 보강 계획

- 작성일: 2026-09-17
- 상태: OPS-00에 이어 OPS-01~05의 공통 이력/검색/컨텍스트, 승인형 Jira 생성/Confluence 추가 게시, OpenAI/Anthropic 계정 조회, 가이드와 모의 통합 시나리오를 구현했다. 개인 테스트 계정의 제한된 합성 Atlassian 게시·조회는 확인했지만 전체 실계정 운영, 사용자 결과 검수, AX 시간 측정은 미완료다. 미지원 세부 범위와 검증 경계는 [실무 검증표](PERSONAL_OPERATIONS_VALIDATION.md)를 따른다. 모든 티켓의 모든 기준을 완료 처리한 것은 아니다.
- 대상: 동일 노트북에서 대화형 AI 도구 또는 하네스 CLI/API로 여러 프로젝트를 운영하는 개인 사용자.
- 목표: 프로젝트를 지정하면 이전 배경과 작업을 읽고, 작업 결과를 보존하며, 대화나 CLI로 다시 찾을 수 있게 한다.
- 사용자 역할: 요구 제시, 티켓별 중요도 확인, 모든 결과 검수, 최종 Git 반영 승인. 시도 횟수는 티켓마다 입력하지 않는다.
- AX 목표: 전체 업무의 사용자 개입 시간을 95% 이상 줄이는 것을 지향한다. 아직 측정하거나 달성한 성과가 아니며, 요구 설명/계획 확인/결과 검수/수습 시간을 포함해 측정한다. 반복 운영 시간 절감은 별도 보조 지표로 구분한다.
- 기록/화면 설계: [개인 Confluence 운영 설계](CONFLUENCE_PERSONAL_OPERATIONS.md).

## 2. 사용 흐름과 보장 범위

1. 사용자가 프로젝트와 작업을 말한다.
2. AI가 공통 시작 명령으로 프로젝트 배경, 최근 이력, 진행 중 작업, 미기록 변경을 확인한다.
3. AI가 요청을 Jira 개인 티켓과 구현/테스트 계획으로 정리한다. 사용자가 중요도를 확인하면 변경분과 공통 최대 시도 3회 정책을 포함해 명시적 계획 승인을 받은 뒤 실행한다. 상세 배경과 결과 문서는 Confluence에 연결한다.
4. 하네스가 실행 상태와 검증 결과를 기록하고, AI는 변경 이유/결정/남은 일을 구조화해 전달한다.
5. 결과 기록과 현재 변경의 연결을 검사한 뒤 검토 준비 상태로 전이한다. 테스트 통과만으로 사용자 검수 완료를 표시하지 않는다.
6. 사용자가 승인한 Git 작업은 기존 승인/fingerprint 절차로 실행하고 기록에 근거를 연결한다.
7. 다른 대화형 도구로 전환해도 동일 프로젝트 ID로 위 자료를 다시 읽는다.

- 하네스 관리 명령의 필수 기록 존재와 근거 일치는 검사할 수 있다.
- AI가 도구 밖에서 나눈 모든 대화나 외부 파일 수정을 자동으로 관찰한다고 주장하지 않는다.
- Git 차이를 통해 미기록 변경을 발견할 수 있지만 과거 의도나 실패 원인은 자동 복원하지 않는다.
- 사용자 승인 없는 commit/push/merge는 기존과 동일하게 차단한다.
- 이번 범위는 같은 노트북에서 실행하고 Jira에 티켓/칸반, Confluence에 배경/결과/결정을 보존하는 방식이다. 로컬 실행 상태와 동기화 대기열은 유지하며 연결되지 않았는데 게시/동기화 완료로 표시하지 않는다.
- 별도 DB나 자체 웹 UI, 여러 PC에서의 동시 실행은 포함하지 않는다. 실제 외부 쓰기는 연결 대상과 게시 범위 확인 후 수행한다.

### OPS-00: 사용자 티켓 설정 및 검수 계약

- 중요도와 구현/테스트 계획을 제시한다. 공통 최대 시도 3회는 읽기 전용 안내로 표시하고 티켓별 입력을 요구하지 않는다.
- 사용자 수정은 DRAFT에서 반영하고 승인 fingerprint에 포함한다. 승인 후 변경된 실행 범위/설정은 재승인을 요구한다.
- 실행기의 최대 시도를 3회 기본값으로 결속하고 누적 시도를 보존한다. 프로세스 재시작/카드 이동만으로 횟수를 초기화하지 않는다. 별도 재개는 사용자 승인 후 새 실행으로 이력을 연결한다.
- 실행 가능한 티켓 사이에서 중요도를 적용한다. 중요도가 높아도 의존성이나 사용자 검수/승인 조건을 우회하지 않는다.
- Jira에서 가져온 중요도/범위는 검증할 입력값이며, 카드 이동이나 체크 표시 자체를 실행/커밋 승인으로 간주하지 않는다.
- 모든 결과의 사용자 검수는 기록과 근거에 연결한다. 자동 테스트 성공, 사용자 검수, 커밋/배포를 각각 표시한다.

검증: 잘못된 중요도/시도 횟수, 승인 이후 설정 변경, 의존성이 있는 중요 티켓, 누적 시도 초과, 페이지 수정만으로 승인 우회 시도.

### 공통 시도 및 알림 정책

- 1회 시도는 구현과 검증을 포함하는 작업 시도다. 개별 HTTP 요청 재시도와 구분하며 전체 시간/호출 예산은 별도로 유지한다.
- 복구 가능한 중간 실패는 원인과 수정 내용을 기록하고 남은 횟수 안에서 재시도한다. 매 시도마다 사용자 알림을 보내지 않는다.
- 3회 소진, 반복된 동일 오류, 인증/권한 문제, 안전 정책 위반 또는 예산 소진은 BLOCKED로 전환하고 즉시 실패 원인/시도 수/필요한 조치를 알린다. 3회를 채우기 위한 무의미한 실행은 하지 않는다.
- 검증 성공 시 REVIEW_READY(구현/검증 완료, 사용자 검수 대기) 알림을 보낸다. 사용자 검수나 Git 반영 완료로 표현하지 않는다.
- 알림은 기존 Telegram 채널을 활용하며 고유 실행/이벤트 ID로 중복을 억제한다. 전송 실패는 별도 대기열로 재전송하고 개발 시도 횟수를 소비하지 않는다.
- 테스트: 1회 성공, 실패 후 성공, 3회 소진, 즉시 중단, 재시작 후 횟수 유지, 알림 실패/중복 전송 억제를 검증한다.

### OPS-01: 공통 작업 기록과 완료 검사

주요 연결점: 단일 프로젝트 complete-task와 task-blocker, 중앙 runner/execution/release, 기존 상태 저장 모듈.

- 중앙 `.harness/local/history/`에 프로젝트/티켓/실행 ID로 구분한 비공개 이력을 저장한다.
- 로컬 기록을 먼저 확정한 뒤 Confluence 전송 대기열에 넣는다. Confluence에 작업/시도별 결과 페이지와 사용자 검수 이력을 연결한다. 원격 실패는 별도의 동기화 상태로 표시한다.
- 이벤트에 스키마 버전, 고유 ID, UTC 시각, 실행 출처, 상태 변화, 변경/검증 근거 참조를 넣는다.
- 결과에는 목표, 실제 변경, 결정과 이유, 실행한 검증/결과, 남은 일, 컨텍스트 갱신 여부를 기록한다.
- 검증 통과와 사용자 승인/Git 반영을 구분한다. 구현 계획을 실제 구현 결과로 복사하지 않는다.
- 코드 수정 작업의 완료에는 현재 Full 검증 근거와 결과 기록을 요구한다.
- 문서/조사 작업은 작업 유형과 확인 근거를 명시하고 코드 검증 완료로 오인되지 않게 한다.
- 기존 force 등 우회 경로도 명시적 미검증/강제 종료 이력으로 남기며 검증 성공을 만들어내지 않는다.
- 필수 기록을 저장하지 못하면 완료를 보고하지 않는다. 실패 상태와 재개 가능한 근거를 보존한다.
- 단일 파일의 atomic rename만으로 다중 파일 처리가 완료된다고 간주하지 않는다. 실행 상태에 저장 의도를 먼저 기록하고, 고유 이벤트 ID로 재처리/중복 방지를 구현한다.
- 완료 과정에서 원본 검증 로그가 정리되더라도 필요한 증거가 영속 이력에 먼저 보존되도록 한다.

검증: 저장 실패, 상태 변경/이력 기록 사이 강제 중단, 재실행 중복, 동시 작성, 기록 없는 완료 요청, 오래된 검증 지문, 예산 소진/blocked 기록.

### OPS-02: 통합 티켓 조회와 기존 이력 연결

주요 연결점: 단일 프로젝트 tasks, 중앙 requests/executions, evidence, deployment.

- 제안 명령: `ticket list`, `ticket show`, `history search`.
- 필터: project, 상태, 기간, 기술/태그, 검색어. 여러 필터를 함께 적용하고 JSON/읽기 쉬운 출력 제공.
- 같은 이름의 티켓은 프로젝트 ID와 출처로 구분한다. 중앙 티켓과 legacy 티켓의 동일성을 추측해 합치지 않는다.
- 기술 정보가 없는 과거 티켓은 미등록으로 표시한다. 키워드 발견만으로 기술 사용을 확정하지 않는다.
- 기간은 어떤 시각을 기준으로 하는지 명시하고 날짜/시간대 경계와 정렬을 일관되게 처리한다.
- 검색용 인덱스는 원본 기록에서 재생성 가능하게 한다. 손상된 자료는 명시적으로 보고한다.
- 기존 archive/done/Git 근거를 읽는 가져오기 미리보기를 제공한다. 실제 반영에는 stable ID와 출처를 기록한다.
- Git 커밋만 존재하는 작업은 가져온 이력으로 표시하며 과거 티켓 승인/검증 성공을 생성하지 않는다.
- 모든 검색 결과에 원본 경로 또는 기록 ID를 연결해 AI의 답변 근거를 확인할 수 있게 한다.
- Jira에서 티켓을 검색하고 Confluence의 공간/라벨/CQL로 관련 문서를 찾는다. 페이지 수정일과 티켓 완료일은 구분하고, 로컬 미동기화 결과도 누락 없이 표시한다.

검증: 두 프로젝트의 같은 티켓 ID, legacy/중앙 자료 혼합, 복합 필터, 한글 검색어, 날짜 경계, 비공개 증빙 외부 출력 방지, 가져오기 재실행, 인덱스 재생성.

### OPS-03: 프로젝트별 재개 컨텍스트와 도구별 진입 가이드

주요 연결점: project-context/profile, 공통 기록, AGENTS.md 및 도구별 진입 안내.

- 프로젝트 ID별 최근 결과/결정/미완료 상태/다음 행동을 중앙 하네스에 저장하고 기존 프로젝트 문서 원본을 참조한다.
- 작업 시작 시 현재 Git 상태 및 문서 hash를 확인한다. 등록 당시 branch/head를 현재 상태처럼 출력하지 않는다.
- 다음 작업 번들에 최근 결과와 관련 결정, 검증 근거를 제한된 크기로 포함한다. 생략 자료는 명시한다.
- 변경 이유나 ADR 수정 여부는 AI가 초안으로 제출하고 근거와 연결한다. 원본 설계 문서를 요약만으로 덮어쓰지 않는다.
- 컨텍스트 변경이 없는 작업도 검토 결과를 기록한다. 의미 있는 결정이 없는데 문서 생성을 강제하지 않는다.
- 재시작 시 lease 만료, 미기록 변경, 부분 저장 상태를 점검하고 재개에 필요한 정보를 제공한다.
- 각 AI 도구의 진입 안내는 동일한 공통 절차를 가리킨다. 도구별 자동 읽기 여부와 실제 확인한 지원 범위를 구분한다.
- 키 없이 대화형으로 쓰는 경우와 별도 키로 API를 호출하는 경우의 과금/실행 주체를 명확히 안내한다.
- 문서는 기존 untrusted-project-input 정책을 유지하고 권한/승인 정책을 바꾸지 못한다.
- Confluence 프로젝트 홈의 배경/결정 페이지를 컨텍스트 출처로 추가한다. 원격 변경과 로컬 캐시의 버전을 표시하고 다른 프로젝트의 자료를 섞지 않는다.

검증: A 프로젝트 결과가 B에 섞이지 않음, 새 프로세스로 재개, 원본 문서 변경 감지, 컨텍스트 한도, 기록 저장 실패, 프로젝트 문서의 지시 주입 처리.

### OPS-04: 공급자 계정 사용량/비용 조회

주요 연결점: 기존 미커밋 provider-usage 서비스와 환경 설정. 기존 변경을 검토해 재사용하고 티켓 범위를 명시적으로 확장한다.

- 조회 데이터를 다음 네 종류로 구분한다: 하네스 관측 사용량, 공급자 보고 사용량/비용, 사용자 설정 예산 대비 잔여액, 공급자가 실제 제공하는 계정 잔액.
- 일반 호출 키와 관리자 조회 자격 증명을 분리한다. 자격 증명은 로컬 환경에서만 읽고 출력/파일/로그에 저장하지 않는다.
- OpenAI와 Anthropic은 공식 사용량/비용 API의 관리자 인증과 페이지네이션을 연동한다.
- Gemini는 사용 제품과 계정의 공식 Monitoring/Billing 조회 경로 및 권한을 확인해 지원 가능한 지표를 연결한다. Gemini API와 Vertex AI의 비용/사용량 범위를 혼합하지 않는다.
- 조회마다 공급자/조직/프로젝트/기간/수집 시각/출처를 명시한다. 같은 금액이나 토큰을 로컬 집계와 중복 합산하지 않는다.
- 비용 잔액, 토큰 예산, 요청 속도 한도, 도구 구독 한도를 동일한 잔여량으로 표시하지 않는다.
- 미설정, 권한 부족, 미지원, 일시 장애, 오래된 캐시를 구분한다. unknown을 0으로 바꾸지 않는다.
- 호출 timeout, 제한 재시도, TTL 캐시를 적용한다. 사용량 조회 장애가 이미 승인된 개발 작업을 임의 실패 처리하지 않도록 한다.
- 한 공급자 조회 실패 시 다른 공급자 결과는 보존한다. 관리자 토큰을 임의 URL로 보내지 않는다.
- 단순 사용량 조회를 위해 모델 추론을 호출하지 않는다. Cloud 조회의 추가 비용/설정이 있으면 명시한다.

검증: 공식 응답 형식 fixture, 여러 페이지 합산, 기간/단위, 401/403/429/5xx/timeout, 부분 성공, 비밀값 비노출, 캐시 시각, 예산과 실제 잔액 구분.

외부 검증: 제공받은 조회 권한이 있는 계정에서만 실제 조회를 확인한다. fixture 통과와 실제 계정 연동 완료를 별도로 보고한다. 공식 잔액 조회가 없는 공급자는 미지원으로 남긴다.

참조: [OpenAI Usage](https://platform.openai.com/docs/api-reference/usage), [Anthropic Usage and Cost](https://platform.claude.com/docs/en/manage-claude/usage-cost-api), [Gemini Billing](https://ai.google.dev/gemini-api/docs/billing).

### OPS-05: 운영 시나리오 검증과 사실 기반 사용 가이드

- 최종 납품물은 README에서 연결되는 `docs/HARNESS_PERSONAL_OPERATIONS_GUIDE.md`다. OPS-00에서 현재 구현 범위의 초안을 작성했으며 전체 운영 가이드와 신규 사용자 재현 검증은 아직 완료되지 않았다. 기존 기술 문서는 참조로 연결한다.
- 목표는 새 사용자가 이전 대화나 작성자의 설명 없이 지원 범위의 설치/운영/복구를 재현하는 것이다. 모든 사용자의 질문이 영원히 없다고 보장하는 대신 아래 시나리오 통과로 판정한다.
- 필수 구성: OS별 준비/설치, 대화형과 API 실행/과금 차이, 기존/신규 프로젝트 등록, Jira/Confluence/Telegram 연결과 권한, 로컬 비밀 설정, 티켓/중요도/승인, 공통 최대 3회 시도와 알림, 결과 검수와 Git 승인, 컨텍스트/검색/이력, 장애 복구, 백업/복원 및 PC 이전의 지원 범위, FAQ.
- 모든 절차는 선행 조건 -> 사용자 행동 -> AI/하네스 행동 -> 실제 명령/화면 값 -> 예상 결과 -> 성공 확인 -> 실패 시 조치 순서로 쓴다. 사이트별 값과 민감 정보는 명확한 placeholder로 구분한다.
- 가이드 수용 검증: 이전 대화 없이 깨끗한 임시 환경에서 설치 -> 연결 -> 프로젝트 등록 -> 티켓 승인 -> 구현/검증 -> 알림/검수 -> 이력 검색을 재현한다. 승인 없는 외부 쓰기/Git 작업은 수행하지 않는다. 인증 실패, 시도 소진, 재시작, 동기화 충돌도 문서의 복구 절차로 확인한다.
- 검증 근거에는 OS/버전, 문서 버전, 실행 결과, 발견한 막힘과 수정 내용을 남긴다. fixture와 실계정, 작성자 자체 검증과 제3자 사용 검증을 구분한다. 미검증 항목이 있으면 전 환경에서 가이드 검증이 완료됐다고 표시하지 않는다.
- 명령/설정/기본값/링크를 실제 CLI와 대조한다. 향후 동작 변경 시 문서와 해당 시나리오를 함께 갱신하는 것을 완료 조건으로 둔다.
- OPS-01 이후 OPS-02/03을 연결하고, OPS-04 결과와 함께 검증한다.
- 두 임시 Git 프로젝트에서 등록, 승인된 계획, 실행, 검증, 결과 기록, 실패/재시작, 재조회까지 E2E로 확인한다.
- 실제 사용자 프로젝트에서는 읽기 전용 조회와 기존 기록 가져오기 미리보기로 확인한다. 변경 실행은 별도 승인된 티켓으로 진행한다.
- 시나리오 가이드에 사용자 요청 예시, AI 작업, 하네스 검사, 저장 위치, 찾는 방법, 한계를 기록한다.
- 구현/fixture 검증/실계정 검증/운영 실증을 따로 표시한다. 하나의 점수나 '완성' 표현으로 대체하지 않는다.
- Confluence 페이지 생성/조회/사용자 편집/버전 충돌/권한 부족/전송 중단/재개를 테스트한다. 실제 연동 계정이 없으면 mock 계약 검증까지만 완료했다고 보고한다.
- AX 기록은 문제, 변경 전후, AI 수행 내용, 사용자 판단, 실패/재작업, 검증 근거, 사용자 개입 시간을 포함한다. 중요도 설정과 검수에 쓴 시간도 누락하지 않는다.
- Full 검증 후 사용자 승인으로 커밋/푸시하며, Windows/macOS/Linux CI 결과를 확인한다.

## 4. 착수 및 완료 판정

- 기존 provider-usage 미커밋 변경과 무관한 파일을 보존하고 보강 티켓별로 변경 범위를 분리한다.
- 구현 순서: OPS-00 -> OPS-01 -> OPS-02 -> OPS-03 -> OPS-04 -> OPS-05. 구현 진행 승인과 실제 외부 게시/최종 Git 승인은 구분한다.
- API 관리자 자격 증명 없이도 로컬 기록/검색/컨텍스트와 API 계약 테스트까지 개발 가능하다.
- 관리자 권한이 없는 공급자의 실계정 검증은 미확인으로 남기고 필요한 설정을 구체적으로 보고한다.
- 기능 완료는 실제 테스트와 근거로 판정한다. API가 제공하지 않는 잔액과 하네스 밖의 모든 대화 자동 수집은 보장 범위에 포함하지 않는다.

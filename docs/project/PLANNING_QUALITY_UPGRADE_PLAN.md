# 계획 작성 품질 고도화 실행 계획

상태: 로컬 구현·격리 리허설 완료 / 최종 게이트 기록은 검증 보고서 참조 (릴리스·유료 평가 별도)
작성일: 2026-11-04
대상: harness-template
성격: 기존 대화형 업무 흐름의 재현성·검증·평가 보강

## 1. 목표와 사용자 경험

사용자는 지금처럼 업무를 말하고, AI가 나눈 업무와 요약을 확인하고 승인한다.
상세 구현·테스트 계획은 기록으로 보존한다. 사용자가 새로운 명령어나 JSON을 직접 작성할 필요는 없다.

변경할 것은 티켓 생성 기능 자체가 아니라 다음 품질 관리 경로다.

```text
업무 요청 + 선택한 프로젝트 자료
  -> 입력 스냅샷과 계획 작성 지침 기록
  -> 대화형 AI 또는 선택형 API가 계획 초안 작성
  -> 구조·출처·경계 자동 검사
  -> 사용자에게 업무 분배·요약·관계·질문 안내
  -> 상세 계획 검수·승인
  -> 기존 티켓 등록·실행·검증·Git 승인 흐름
```

1차 완료의 의미는 같은 입력과 출력에 같은 계약 검사를 적용하고, 실패·수정·평가 근거를 남기는 것이다.
대화형 모델의 내부 프롬프트와 샘플링까지 재현하거나, 동일 모델의 동일 답변을 보장하는 것이 아니다.

## 2. 현재 구현 확인과 재사용 원칙

2026-11-04 로컬 `codex/operational-binding` 작업 공간에서 확인한 기준이다.
현재 라우팅·알림·메모리 보강은 미커밋 상태이며 본 계획은 이를 덮어쓰거나 main 반영 완료로 취급하지 않는다.

| 기존 요소 | 확인한 기능 | 이번 작업 |
|---|---|---|
| `request-plan.js`, `request-command.js` | 상세 티켓, 의존성, 위험도, 계획 지문, DRAFT 승인 | 새 티켓 체계를 만들지 않고 재사용 |
| `project-context.js`, `context-references.js` | 크기 제한, 명시 문서 참조, 해시/원격 버전 검사 | 실제 계획 입력 스냅샷을 연결 |
| `model-eval-command.js` | dry-run/live, 호출 예산, 입력·정책 결속, 토큰·시간, 비교·인간 검수 | 상세 계획 평가 유형을 추가; 기존 평가 유지 |
| `model-eval-oracle.js` | 구조, 프로젝트, 검증 명령, 의존성, 승인 경계 검사 | 출처/실제 자료 계약 검사 추가; 의미 평가와 분리 |
| `evals/regression/ticket-cases.json` | 합성 계획 사례 3개 | 기존 사례 보존; 자료 기반 사례를 별도 유형으로 추가 |
| `provider-request.js`, `provider-usage.js` | 공급자 호출·관측 사용량 | 선택형 API 생성에서 재사용 |
| 기존 실행·기록·Atlassian 연동 | 승인 후 티켓/실행/기록 관리 | 승인 전 원격 쓰기나 자동 개발을 추가하지 않음 |

기존 JSON 직접 입력·레거시 요청 계획·승인 지문·평가 기록을 그대로 읽을 수 있어야 한다.
신규 계약은 새 품질 관리 경로에서 생성·등록되는 초안에 적용하고, 기존 승인 파일을 일괄 수정하지 않는다.

## 3. 포함 및 제외 범위

### 포함

- 실제 요청과 선택 자료의 출처 스냅샷.
- 대화형 출력과 API 출력에 공통으로 적용되는 계획 계약.
- 확인된 사실 / 구현 제안 / 미확정 사항의 구분.
- 초안·수정·검수·승인의 근거 연결과 stale 검사.
- 저장된 출력의 오프라인 평가 및 선택형 live 비교.
- 누락·근거 없는 사실 주장·경계 준수·사람 수정의 평가 기록.
- Windows/macOS/Linux를 고려한 Node 테스트와 운영 안내.

- 요청 전체를 자동으로 수집하는 기능, 모든 문서·저장소의 일괄 전송.
- 새 Jira 보드·Confluence 공간·외부 게시 체계.
- 모델 평가의 자동 정답 판정, 환각 0 보장, 자동 최우수 모델 선정.
- 무승인 API 비용 발생, 원격 쓰기, 개발 실행, commit/push/merge.

## 4. 최소 입력 계약

| 항목 | 계약 |
|---|---|
| 요청 | 원문과 요청 ID를 보존. AI 요약으로 원문을 대체하지 않음 |
| 대상 프로젝트 | 등록된 ID와 승인된 프로필 지문. 다중 프로젝트는 명시적 목록 |
| 문서 | 기존 허용 경로/Confluence 참조 규칙으로 선택한 자료만 사용 |
| 코드 근거 | 필요한 파일/구간만 명시적으로 선택한 읽기 전용 스냅샷. 기존 Markdown 참조 허용 범위를 임의로 확대하지 않음 |
| 자료 식별 | source_id, project_id, 상대 경로 또는 페이지 ID, 해시/버전, 포함 구간과 내용 |
| 부재 자료 | 필수/선택 자료 누락과 제외 이유를 기록; 내용을 추정해 채우지 않음 |
| 실행 가능 정보 | 프로젝트 프로필의 승인된 검증 명령 목록과 정책 |
| 기록 | 입력·스냅샷·지침 버전의 fingerprint, 생성 방식, 시간 |

기존 context 제한을 재사용하고, 한도 초과 시 필수 자료를 몰래 자르지 않고 범위 축소를 요청한다.
비밀 파일·환경 변수·토큰은 수집 대상이 아니다. 명시적으로 선택한 업무 자료도 비밀값이 발견되면 전송을 중단해 정제하도록 안내한다.
탐지만으로 모든 민감정보를 제거했다고 보장하지 않는다. 회사 자료의 외부 API 전송은 회사 정책과 사용자 허용을 전제로 한다.
프로젝트 문서는 untrusted input이며 승인·예산·도구 권한을 부여하지 않는다.

## 5. 최소 출력 계약과 검수

### 계획 본문

기존 `goal`, `assumptions`, `exclusions`, `tickets[]`를 재사용한다.
티켓에는 프로젝트·종류·우선순위 제안·업무 라벨·위험도/근거·범위/제외 범위·수용 기준·구현 단계·테스트 계획·검증 명령·의존성을 둔다.
기본 최대 시도는 기존 정책의 3회이며 사용자가 수정한다. 이번 작업에서 자동 재시도 예산을 새로 늘리지 않는다.

### 품질 근거 부록

기존 티켓 스키마에 임의 필드를 섞어 유실시키지 않도록 별도 버전 관리 artifact로 저장한다.
새 품질 관리 초안에는 해당 artifact의 ID/지문을 연결하고 승인 지문에도 결속한다.
기존 레거시 계획에 이 필드를 요구하거나 기존 승인을 재작성하지 않는다.

| 내용 | 규칙 |
|---|---|
| 확인된 사실 | source_id와 인용 구간, 해당 사실을 표현하는 문장 |
| 구현 제안 | 신규/변경 작업임을 명시하고 대응 요청·제약에 연결 |
| 미확정 사항 | 질문, 영향받는 티켓, 승인 전 반드시 해결해야 하는지 기록 |
| 경로 근거 | 기존 경로 참조인지 신규 생성 제안인지 구분 |
| 티켓 관계 | Git 선행 의존 / 문서 참조 / 단순 관련을 구분. Git 의존성에 모두 넣지 않음 |
| 사용자 안내 | 업무 분배·요약·관계·권장 순서·중요 질문. 상세 계획은 별도 열람 가능 |

중요 미확정 사항이 남으면 검토 가능한 초안으로만 저장하고 기존 요청 승인 진입을 차단한다.
이 상태를 실제 개발 실행 실패의 BLOCKED 티켓과 혼동하지 않도록 초안 검증 결과로 표현한다.

### 자동 검사와 한계

- 구조, 필수 필드, 알려진 프로젝트, 의존성 DAG, 위험도 값, 출처 ID/해시/인용 구간을 검사한다.
- 기존 파일이라고 주장한 경로는 승인된 스냅샷에서 확인한다. 신규 경로 제안은 존재하지 않는다는 이유만으로 실패시키지 않는다.
- 검증 명령은 승인 프로필의 명령을 사용한다. 새로운 명령은 미확정 제안으로만 남기며 실행하지 않는다.
- 계획·근거 artifact·프로필·참조 자료가 바뀌면 이전 품질 검사/승인을 새 초안에 재사용하지 못하게 한다.
- 인용 구간이 실제 있다는 것은 주장과 인용의 의미적 일치를 보증하지 않는다.
- 자동 검사를 통과해도 계획의 타당성·누락·근거의 의미는 사람이 판단한다.

## 6. 대화형과 선택형 API 실행

### 기본: 대화형 유지

호스트 AI가 공통 입력을 받아 초안을 작성하고, 하네스에 공통 출력 artifact를 전달한다.
하네스는 검사·기록·사용자 검수용 요약을 제공한다. 대화형 사용을 이유로 별도 API 호출을 강제하지 않는다.
생성 방식은 interactive-host로 표시하고, 호스트가 제공하지 않은 실제 모델명·토큰·숨은 프롬프트는 unknown으로 기록한다.
API 호출과 대화형 결과를 같은 실험처럼 혼합 비교하지 않는다.

### 선택: API 생성

기존 provider 호출·usage·모델 라우터를 사용하고 초안 작성에만 도구 권한을 부여한다.
기본은 dry-run으로 전송 자료·선택 모델·호출 한도를 보여준다. 실제 호출은 명시적인 live 선택과 사용자 비용/전송 승인이 있어야 한다.
생성 1회가 기본이며 재호출이 필요하면 실패 근거와 남은 한도를 표시한다. 검증 실패 시 무한 자동 재생성하지 않는다.
요청 수는 HTTP 재시도까지 구분 기록하고 출력 토큰·응답 크기·시간 한도도 적용한다.
고위험 작업의 fast 충돌 차단 등 기존 정책은 유지한다. 계획 생성 단계에서는 보수적인 위험도 제안을 사용하며 최종 위험도 판단은 사용자 승인 대상이다.

구체적인 새 CLI 옵션명은 구현 티켓에서 기존 `request`/`eval` 명령군에 최소한으로 정한다.
본 문서의 설명은 현재 존재하는 명령으로 오해할 수 있는 사용법을 추가하지 않는다.

## 7. 작업 분할안

사용자 승인 후 아래 T01~T05를 로컬 티켓으로 발급했다. 구현은 같은 작업 브랜치에서 순차 통합한다.
모두 기본 최대 3회 시도를 제안하며, 중요도·범위·위험도는 사용자 수정 가능하다.
업무 라벨 제안: `계획품질`, `평가근거`.

### T01. 계획 입력·출력 및 출처 계약

- 중요도 P1 / 위험도 medium / 제안 모델 standard.
- 범위: 공통 artifact 스키마, 입력 manifest, 사실/제안/질문 및 경로 종류, 구간·해시·버전 규칙, 레거시 호환 계약.
- 대상: 기존 request/context 모듈, 필요 시 전용 planning-contract 모듈, 해당 계약 테스트.
- 구현: 기존 스키마와 매핑 정의 -> 예시 입력/출력 작성 -> 엄격한 파싱·크기/경로 검사 -> 호환 fixture 작성.
- 검증: 잘못된 프로젝트/ID/유형/필드, 경로 탈출·junction, 누락 자료·초과 입력 거부; 기존 계획 원본·지문 무변경 로딩.
- 수용: 동일 contract를 대화형/API가 사용하며, 존재하지 않는 신규 파일 제안과 허위 기존 경로 참조가 구분됨.
- 의존성 없음.

### T02. 계획 근거 기록·검사 및 승인 연결

- 중요도 P1 / 위험도 medium / 제안 모델 standard; 승인 경계 검토는 strong 제안.
- 범위: 로컬 artifact 보존, 계획과 근거 지문 결속, 공통 검사, 질문 미해결 및 stale 승인 차단, 검수 요약.
- 대상: `request-plan.js`, `request-command.js`, 로컬 원자적 상태 저장, 프로젝트 문맥 검사, 관련 회귀 테스트.
- 구현: 저장 경로/버전 결정 -> 대화형 출력 수신 -> 검증 결과 저장 -> 명확한 초안/검수 상태 안내 -> 기존 승인 진입 연결.
- 검증: 문서·근거·계획 변조/교체, 재사용 승인, 검사 실패 후 승인, 필수 질문 미해결, 신규 제안 허용, 원격 쓰기/명령 실행 0회.
- 수용: 사용자는 지금처럼 요약 검수 후 승인하고, 상세 근거는 보존되며 승인 후 수정은 재검사 필요.
- 실행 의존성: T01.

### T03. 공통 계약을 사용하는 선택형 API 초안 작성

- 중요도 P2 / 위험도 medium / 제안 모델 standard.
- 범위: 기존 provider·라우터 연결, 버전 관리 프롬프트, dry-run/live 구분, 비용/전송 경계, 응답/오류 기록.
- 대상: `provider-request.js`/usage/라우터 호출부 재사용, 기존 request 진입점, 전용 계획 생성 프롬프트, mock transport 테스트.
- 구현: 입력을 공통 prompt로 구성 -> 도구 없는 API 호출 -> 응답 크기/시간/JSON 검사 -> T02 경로로만 초안 저장.
- 검증: 3사 mock 응답, malformed/과대 출력, timeout/429/quota, 호출 한도, credential 비노출, live 승인 없는 네트워크 호출 0회.
- 수용: API 결과도 대화형과 동일 검사를 받으며 실행/원격 등록으로 직접 넘어가지 않음. API 키 없는 기본 대화형은 회귀 없이 유지.
- 실행 의존성: T02. T04의 평가셋 작성과 병렬 가능하나 공통 모듈 변경은 순차 통합.

### T04. 자료 기반 계획 평가와 사용자 수정 기록

- 중요도 P1 / 위험도 medium / 제안 모델 standard.
- 범위: 기존 eval 명령 확장, 자료 기반 평가 사례, 저장 응답의 오프라인 채점, 인간 루브릭·수정 이력, 비교 근거.
- 대상: `model-eval-command.js`, 별도 계획 품질 oracle, `evals/` 신규 데이터 유형, 기존 eval 회귀 테스트.
- 구현: 기존 3개 사례/결과 보존 -> 고정 자료 사례와 정답 루브릭 추가 -> 공통 계획 validator 재사용 -> 인간 평가/수정 기록 -> 조건이 같은 결과 비교.
- 검증: 구버전 결과 로딩, oracle/자료/루브릭 버전 변경 시 비교 거부, 중단 live 결과 미완료 유지, review 변조/오래된 검수 거부, 오프라인 네트워크 0회.
- 수용: 자동 계약 통과와 인간의 의미 평가가 별도 표시되고, 근거 없는 모델 순위나 미측정 숫자를 출력하지 않음.
- 실행 의존성: T01. 실동작 연결은 T02와 T03 결과를 참조하며, 서로 다른 Git 분기의 자동 fan-in은 하지 않음.

### T05. 통합 리허설·가이드·결과 보고

- 중요도 P1 / 위험도 medium / 제안 모델 standard.
- 범위: 단일/다중 프로젝트 fixture E2E, 최종 검사, 사용 가이드, 로컬 실제 요청 시범 평가. 유료 live 비교는 별도 승인 조건부.
- 대상: CLI smoke/E2E 테스트, `tests/harness-cli/run.js`, 사용자 가이드, 평가 결과 기록.
- 구현: 대화형 초안 수신 -> 실패 교정 -> 사용자 검수 -> 계획 승인까지 격리 리허설; API 경로는 mock으로 같은 계약 확인.
- 검증: 단위 테스트, 프로세스 CLI, 기존 모델/리뷰 평가, 전체 test/lint/Full/drift; 원본 프로젝트·외부 Jira·Git mutating 호출 없음 확인.
- 수용: 가이드로 재현 가능한 예시, 실패/한계 보고, 미실행 항목 명시. CI/실계정 통과를 로컬 모의 결과로 대신 주장하지 않음.
- 실행 의존성: T02/T03/T04. 공유 CLI 변경은 한 작업 브랜치에서 순서대로 통합.

권장 순서: T01 -> T02 -> T03 -> T04 -> T05.
T03/T04의 논리적 병렬 가능성과 별개로, 이번에는 브랜치 증가와 충돌을 줄이기 위해 순차 작업을 기본 제안한다.

## 8. 평가 계획

### 사례 구성

최초 pilot은 자료가 고정된 6~9개 사례로 작게 시작한다. 이는 통계적으로 충분한 모델 우열 증명이 아니다.
단일 프로젝트, 독립 다중 프로젝트, 선행 관계, 누락 자료, 미지원 요구, 문서 내 지시 주입, 기존/신규 경로, 수정 요청을 포함한다.
개발용과 보류 평가용 사례를 구분하고 유사한 변형을 양쪽에 섞지 않는다. 보류 사례를 보고 개선하면 그 사례는 개발용으로 전환하고 새 보류 사례를 확보한다.
1차 자료는 합성 또는 비밀정보를 제거한 고정 자료를 사용한다. 실제 업무 자료 사용 여부는 별도로 승인한다.
정답 루브릭/기대 조건은 모델 입력에 섞지 않는다. 실제 요구사항 원문은 당연히 입력에 포함한다.

### 지표와 분모

| 지표 | 측정 방식 | 한계 |
|---|---|---|
| 구조/출처 계약 통과 | 전체 응답 중 공통 validator 통과 수 | 의미적 correctness 아님 |
| 요구사항 누락 | 사람이 정한 필수 조건 중 빠뜨린 수 / 전체 필수 조건 | 조건 목록·판정 기준을 먼저 고정 |
| 근거 없는 사실 주장 | 사람이 검토한 사실 주장 중 근거 없는 주장 수 / 사실 주장 수 | 신규 구현 제안과 구분; 주장 수 0은 N/A |
| 경계 준수 | 질문/보류가 필요한 기회 중 올바르게 처리한 수 | 불필요한 질문도 별도 기록 |
| 사람 수정 | 내용상 수정·추가·삭제 건수, 검수 시간, 전후 artifact | 문자열 edit distance는 보조; 적게 수정했다고 고품질은 아님 |
| 사용량·시간 | 관측 토큰, 요청/HTTP 재시도, 생성 지연과 실패 포함 합계 | 호스트 미제공 값은 unknown; 로컬 정적 추정과 구분 |
| 비용 | 공식 가격·기준일이 있는 설정으로만 추정 | 요금표 미설정 시 unknown; 계정 청구 금액 아님 |

비교는 입력 snapshot, 공통 prompt, oracle/루브릭, 예산·재시도 정책과 생성 경로가 같을 때만 한다.
API 모델별 고정 기준선을 먼저 비교하고 3-Tier 동적 라우팅의 품질/비용 이득은 후속 실험으로 분리한다.
작은 표본·1회 실행·fixture 결과를 일반적인 모델 성능이나 실무 절감률로 표현하지 않는다.

### 승인 기준

- 결정론적 테스트: 새 성공/실패 경로와 기존 회귀 테스트 전부 통과.
- 사전 지정한 승인 우회·출처 위조·위험 명령 시나리오는 모두 거부. 이는 임의 공격 전체의 차단 보장이 아님.
- 의미 품질은 건수·분모·오류 사례·수정 내역을 사용자에게 제출하고 사용자가 평가한다. 근거 없이 누락률 0% 등의 목표를 달성했다고 선언하지 않는다.
- live 비교를 하지 않아도 코드 구현/모의 검증 상태는 보고할 수 있으나 실제 모델 품질 평가 완료로 표시하지 않는다.

## 9. 저장·호환·롤백·운영 경계

- 개인 요청·원문·응답·수정 이력은 Git ignored 로컬 상태에 저장한다. 공개 evals에는 정제된 합성 fixture만 둔다.
- 새 원장은 기존 암호화 백업의 허용 목록/미리보기에서 누락 여부를 확인한다. 실행/승인을 다른 PC로 복원해 재사용하는 권한은 부여하지 않는다.
- 검사·승인 지문은 관리형 경계이며 OS sandbox나 호스트의 임의 파일 쓰기 차단이 아니다.
- 원격 Jira/Confluence 등록과 개발 실행은 기존 승인 후 흐름을 따른다. 이번 초안 생성만으로 원격 쓰기를 승인하지 않는다.
- T01~T05 변경은 기존 기능과 별도 모듈/테스트로 구분한다. API 생성 비활성화 시 기존 대화형 흐름이 계속 동작한다.
- 롤백은 코드 변경의 선택적 되돌림과 기능 미사용으로 한다. 사용자 원본·이전 artifact를 자동 삭제하지 않는다.
- 기존 operational-binding 미커밋 및 개인 파일은 보존한다. 새 구현 착수 시 기준 브랜치·기존 변경을 다시 확인하고, main 직접 수정·자동 commit/push는 하지 않는다.

## 10. 사용자 승인 요청 요약

1. 대화 방식은 유지하고 위 T01~T05의 품질 관리 보강을 구현한다.
2. 기본 3회 시도·P1 중심 중요도·medium 위험도 및 사람 읽기용 라벨은 제안값이며 조정 가능하다.
3. 이번 승인은 코드·합성 fixture·격리 mock 검증 범위다. 실제 외부 API 호출·회사 자료 전송·원격 게시·Git 반영은 별도 승인한다.
4. 최초 계획 작성 시에는 작업을 시작하지 않았으며, 이후 사용자 구현 승인으로 T01~T05를 진행했다. 실제 유료 호출·외부 게시·Git 반영 승인은 포함하지 않는다.

구현 명령 및 한계는 [계획 품질 가이드](../PLANNING_QUALITY_GUIDE.md)를 따른다.
구현·테스트 근거 및 미실행 범위는 [검증 기록](PLANNING_QUALITY_VERIFICATION.md)에 정리한다.
